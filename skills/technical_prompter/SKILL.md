# WowCube Technical Prompter

> **This skill is Stage 2 of the `cube_orchestrator` pipeline.** The orchestrator invokes it (via the Skill tool) when a GDD exists but `plans/<game>_prompts.md` / `plans/<game>_assets.json` do not. It is not a user-facing entry point — the user enters through `cube_orchestrator`, which routes here.

Decompose a Game Design Document into the smallest possible vertical-slice implementation prompts, where each prompt produces a testable increment. The prompts and asset manifest are the Stage 2 artifacts; `cube_orchestrator` checkpoints them with the user (stepwise mode; auto-accepted in autonomous mode) and then drives Stage 3 (`cube_asset-builder`).

**Engine facts come from one place:** `<skills>/templates/app_ai_template/API.md` (limits, art tiers, sound mixer, saves, callbacks) and the annotated `templates/app_ai_template/src/app_ai_template.h`. `<skills>` is this skills repository (the folder holding `skills/`, `scripts/`, `templates/`), as in `cube_orchestrator`; write its real path wherever a prompt names a file. The SDK baseline is **octavios dev** (2026-10-21, `609d5ae` or later): the mixer, `SND_play_quad`, the save API, per-screen taps and `OCT_APP_SEMVER` need it.

## When to Use

- `cube_orchestrator` routed here because a GDD exists but `plans/<game>_prompts.md` or `plans/<game>_assets.json` is missing
- The orchestrator needs prompts and the asset manifest before it can drive Stage 3 (assets)

Do not trigger this skill directly for "implement this" / "start coding" requests — those are owned by `cube_orchestrator`, which routes here as Stage 2.

## When NOT to Use

- No GDD exists yet — the orchestrator will route to Stage 1 (`cube_game-designer`) first
- The request is to modify existing running code — this produces fresh implementation prompts

## Constraints

- **Assets are made at Stage 3 by `cube_asset-builder`** before any prompt is implemented: sprites drawn by Codex through `cube_art-director` (style lock, strict QA), sounds from user-approved CC0 recordings built with `scripts/sound_kit.py` (synthesised placeholders only as a fallback), packed into `app_<game>/`. This skill owns the ASSET MANIFEST (`plans/<game>_assets.json`) — the complete, validated list of every sprite and sound the game needs.
- **Prompts MUST reference assets by exact final identifier**:
  - Single sprite: `BMP_<name>` (e.g. `BMP_coin`).
  - Animation sequence: `BMP_<base>` (first frame alias) and `BMP_<base>_end` (last frame alias) — both generated by the packer for a zero-padded `_NN`/`_NNN` sequence, zero-based (`_00…`) or one-based (`_01…`).
  - Sound: the string literal `"<name>.mp3"`, resolved ONCE with `SND_getAssetId("<name>.mp3")` in `on_init` and cached (the ids header also carries `SND_<name>` constants; never look names up every tick).
- **Every `BMP_*` or `"<name>.mp3"` referenced in a prompt MUST exist in the manifest.** The code will fail to compile (or a sound will be missing) otherwise.
- **Generated and scaffolded files are never hand-edited by prompts**: `src/app_<game>_ids.h` and `index.bin` (packer output); `src/app.h` and the identity lines of `src/app_metadata.h` — `APP_VERSION_MAJOR/MINOR/PATCH` + `APP_VERSION OCT_APP_SEMVER(...)`, `APP_GUID1` (random per game), `APP_TITLE`, `APP_CATEGORIES`, `APP_COLORS` (scaffolder and `repack_app.py` own them).
- **Code agents work in `src/app_<game>.h`.** Two exceptions a prompt may name explicitly: the saves prompt creates `src/app_save.h` and switches on its `#include` plus `APP_HAS_ON_SAVE` / `APP_HAS_ON_SAVE_SYNCED` in `src/app_metadata.h`; a procedural-drawing prompt switches on `APP_HAS_PROC_DRAW` there.

## Core Principle

**Each prompt = the smallest testable vertical slice.**

The first prompt produces something visible. Every subsequent prompt adds exactly one testable behavior. An agent executing any single prompt can verify their work before moving to the next — and the orchestrator verifies it itself on headless screenshots of all 24 screens taken from an autoplay build, so every Verification section must be checkable that way.

## Workflow

### Step 1: Read the GDD

Locate and read the game design document (typically `plans/<game_name>_gdd.md`).

Extract:
1. **Game objects** — types, behaviors, visual descriptions
2. **Game states** — flow between menu, playing, win, lose
3. **Mechanics** — each gameplay mechanic described
4. **Controls** — what each input does
5. **Assets** — full sprite and sound list, the Art Style section, the Music & Sound section
6. **UI elements** — score display, menus, feedback
7. **Progression and Tunables** — levels, difficulty, the tunables table
8. **Composition** — what lives on one screen / one face / every face; panoramas; unique objects
9. **Saves** and **Testing & Delivery** (autoplay, mute, playfield pin, icon, video)

### Step 2: Study the API

Read `<skills>/templates/app_ai_template/API.md` and `templates/app_ai_template/src/app_ai_template.h` — the SOURCE OF TRUTH for OctaviOS API usage, limits and patterns. Do NOT copy demo code from it. Read `skills/cube_game-designer/references/GAME_FEEL.md`: its "hooks" section becomes the test-hook block below.

### Step 3: Plan the Decomposition

Break the game into the smallest logical vertical slices. Follow this ordering principle:

1. **Foundation** — scaffold, data structures, engine init, background, **the TEST HOOKS and TUNABLES blocks** (Step 5a)
2. **First visual** — something appears on screen (even one sprite on one face)
3. **Static layout** — all faces show their initial state
4. **First input** — one input type produces a visible response
5. **Core mechanic** — the primary gameplay loop, one piece at a time (each extends the autoplay bot)
6. **Secondary mechanics** — boosters, blockers, special behaviors
7. **Game states** — win/lose detection, state transitions
8. **UI** — score display, menus, game over screen
9. **Audio** — music bed, then event sounds (Step 5b)
10. **Saves** — only when the GDD has a Saves section (Step 5c)
11. **Polish** — glides, edge cases, balance tuning (tunables only)

**Decomposition rules:**
- Each slice must produce something the agent can SEE on the 24-screen screenshots (or, for audio, in the sound-event log)
- If a mechanic has sub-parts, split them (e.g., "gravity" = "detect empty space" + "move figures down" + "spawn new figures" as 3 prompts)
- Never combine unrelated behaviors in one prompt
- If a prompt takes more than ~100 lines of code to implement, split it further

**Manifest rules** (validator-enforced unless marked):

- **Names** match `[a-z][a-z0-9_]*` (**a letter first**: the name is used verbatim as the file, the `index.bin` record and the `BMP_`/`SND_` id), are **at most 23 characters** (octavios asset names are `char[24]` with the NUL), unique within sprites and within sounds, and never reserved: `pal`, `0`, `icon`, `zero`, `none`, `last`, `ico`, `ico_idle`, `ahover`, `bmp_none`, `bmp_last`, `bmp_0`, `map_none`, `map_last` (the packer or the ids header uses them). Never shaped like a font glyph the packer generates (`font_<x>_<5 digits>`), and no sprite named like an animation's alias (`<base>` or `<base>_end` when `<base>_00…` frames exist).
- **Animation frames**: zero-padded suffix, **2 or 3 digits**, contiguous, starting at either `_00`/`_000` (zero-based) or `_01`/`_001` (one-based), one digit width per sequence. Set `anim: "<base>"` and `frame: <N>` matching the numeral.
- **`description`** is required on every sprite and sound: the human brief (what it is, where it is used, its on-screen size).
- **`background`** (`"key"` | `"opaque"`) on **every** sprite (`validate` rejects a sprite without it; art.py decides from it whether to ask for a key backdrop and key it):
  - `"key"` for cut-outs — characters, props, effects, UI pieces, text: drawn on a flat chroma-key backdrop and keyed away;
  - `"opaque"` for full-canvas pictures — backgrounds, sky/forest strips, tiles, full-colour art.
- **Sizes** are authored (pre-upscale) pixels, both sides 1..120 unless `flags.fullsize` is set. The engine upscales every non-fullsize sprite ×2 at draw time, so `size` is HALF the on-screen size: **authored size = intended on-screen size ÷ 2** (full screen → `[120, 120]`; half the screen each side → `[60, 60]`; a quarter → `[30, 30]`). A background without `fullsize` is `[120, 120]`, never `[240, 240]`.
- **Tiers**: `color` (`"palette"` default, or `"full"`) plus `flags.fullsize` select the art tier; the tier table and the render rules are in `templates/app_ai_template/API.md`. Manifest consequences:
  - `"full"` = RGB565 with **no transparency**: every full-colour sprite must carry `"flags": {"alpha": false}` (alpha defaults to true and is an error on full colour).
  - Any side > 120 **requires** `flags.fullsize` (draws 1:1, native size up to `[240, 240]`).
  - `dither: true` only on `"full"` sprites (recommended for smooth gradients and photographic art).
  - **Opaque full-screen backgrounds: `color: "full"`** + `"flags": {"alpha": false, "bg": true}` (a palette `bg` sprite once rendered magenta).
  - Maximum quality (no compromises) = `color: "full"` + `flags.fullsize` + `dither: true`.
  - Pick the tier by what the art needs (transparency, native sharpness, colour depth); there is no practical pack-size limit — never cut frames or downgrade art to save bytes.
- **Animation timing**: at most **20 fps** (the engine ticks 20 times/second); no clip-length or frame-count budget. A full-colour fullsize animation only when the user asked for one, with a "handle carefully" note in its description. **One animated full-screen (fullsize) picture per physical module** is the owner's guideline, **informational until the owner confirms it** (ordinary sprite animations are not limited): when two such pictures would share a module (a face's four screens are four modules, adjacent faces share two, opposite faces none), say so in their descriptions; it blocks nothing.
- **Sets**: `group` names a family that must read as one (one character's idle/walk/shoot/hurt, one prop family). Members of one group that must match share the same `size`, so Stage 3 fits them at one scale.
- **Tilt games and the autoplay bot**: the hidden simulator cannot tilt the cube, so every gravity/tilt read goes
  through one input struct (e.g. `vars.input.tilt`) that `on_tick` fills from `OCT_TM_gravity_*` normally and from
  the bot when `<GAME>_DEBUG_AUTOPLAY` is on; mechanics never read the gravity API directly.
- **Panoramas** (not validated; read by Stage 3): scenery that spans screens is one picture split per screen, never one tile repeated on every screen. List the pieces as ordinary opaque sprites (`<name>_r<row>c<col>`, `[120, 120]`, `color: "full"`, `"flags": {"alpha": false}`) and describe the source picture once in a top-level `"_panoramas"` object: `{"sky_night": {"size": [240, 240], "grid": [2, 2], "pieces": ["sky_night_r0c0", "sky_night_r0c1", "sky_night_r1c0", "sky_night_r1c1"], "gen_prompt": "..."}}` (row-major). The default is one face whose left and right edges tile: shown upright on the four side faces it runs continuously around the cube. The prompts place piece `r<row>c<col>` on that screen of the face as the player sees it upright: with the template's `uprightAround(playfield, side, ...)` (up points at the playfield) at the screen-fill centre `±QUAD_FILL` (119.5). Unique objects (moon, sun) are separate sprites placed once. Optional `"anchors": ["<asset>", ...]` in the panorama entry names the style anchors Stage 3 attaches (scenery, not characters); a front view around a top-down playfield says "a flat front view, not an overhead view" in its `gen_prompt`. Each piece still needs a `gen_prompt` (`validate` requires one): describe what that quarter shows ("upper-left quarter of the night sky panorama: dark clouds, the moon's glow at the right edge"); Stage 3 cuts the pieces from the panorama before the batch, so the piece prompts are a fallback, not the plan.
- **Sounds**: `duration_ms` is the planned length (the engine has no length cap; the validator only rejects typos above 10 minutes); `event_type` is one of `pickup, hit, ui, ambient, music, default, shoot, spawn, attack, hurt, death, win, lose, jump, step, explode, voice, alert, transition`. The music bed is `event_type: "music"`, 10-20 s, present unless the GDD explicitly says "no music"; Stage 3 replaces its `duration_ms` with the measured loop length. One sound per moment: when two events coincide (a shot that kills) list one combined sound. `description` names the mood and the planned source (CC0 recordings).
- **`_style`** (top level; ignored by the validator): one 60-120 word paragraph derived from GDD §1 Art Style — viewpoint, palette words, outline, shading, light, detail level, pixel grid. Stage 3 copies it into `assets_<game>/style/STYLE.md` as the `## Prompt block`, which art.py puts in front of every prompt; the style frame the user approves is drawn with it. It is written ONCE here and never repeated inside a `gen_prompt`.
- **Launcher icon**: one sprite `launcher_icon` (`icon` is reserved): `[160, 160]`, `color: "palette"` + `"flags": {"fullsize": true}` (so the PNG keeps its transparent corners through processing), `background: "key"`, `group: "icon"`, a `gen_prompt` for a **flat-top hexagon badge** (horizontal top and bottom edges, points left and right, thick outline) showing what GDD §10 asks for, in the game's style. Stage 3 draws it with the set and copies it to `app_<game>/art/icon.png`; game code never references it.
- **`icon`** (top level, optional): the launcher icon's **packed** tier — `{"color": "full"|"palette", "side": ..., "dither": ...}`; `"full"` (default) allows sides 1..240 (default 160), `"palette"` only 120 or 240 and no dither. Be honest about the default: a full-colour icon is RAW565 with **no transparency**, so the badge's transparent corners render black on the dark launcher. When the GDD wants real transparent corners write `"icon": {"color": "palette", "side": 120}` (drawn ×2) or `240` (fullsize); the packer resizes the 160×160 PNG to that side and keeps its alpha (API.md, Art tiers).

Write the manifest to `plans/<game>_assets.json`.

### Step 4a: Write a `gen_prompt` for every sprite

Each sprite carries a `gen_prompt`: what to draw, for Codex's image tool (through `cube_art-director`'s art.py, which adds the style block, the attached style anchors, the square canvas and the backdrop sentence itself). The validator rejects an empty one.

**Derive each prompt from the GDD, not from imagination** (§3 Game Objects, §7 Assets, §6 Composition).

**A `gen_prompt` says:**
1. **Subject** — what the object is, its distinctive features and local colours ("grey-green rotting skin, torn dark-brown clothes, both arms stretched toward the top of the image").
2. **Orientation** — which way it faces in the image (characters usually face the top of the image in top-down games); the viewpoint only when it differs from the game's (`"flat front view"` for text and UI in a top-down game).
3. **Frames** — for `anim` frames: "frame k of N of a <cycle>: <phase>" plus what stays identical ("same character as frame 0; only the shoes and the hem change"). Stage 3 attaches frame 0 as the subject reference for every later frame.
4. **Framing** — one subject. For non-square sizes, the proportion ("a long horizontal bar, about 3:1"): the canvas is square and processing crops to the subject and fits it into `size`. Cell-filling objects: "fills most of the canvas". Opaque pictures: where things are ("tree line along the bottom 45 %, sky above").
5. **Effects** (flash, blast, slash, particles): "no characters, no objects, only the effect" — otherwise the style anchor's character leaks in.
6. **Text sprites**: the exact text in quotes, "letters only".

**Never write:**
- "transparent background" (the model cannot draw transparency; `background: "key"` makes art.py ask for a flat backdrop and key it);
- "exactly WxH pixels" or any pixel size (the model draws a 1024×1024 canvas; fitting to `size` is processing);
- the style paragraph (it is `_style`);
- the backdrop colour — except `#00FF00` to force a green key on a pink/magenta subject (art.py also picks green by itself when the prompt says pink, magenta, fuchsia, purple or violet).

Keep each prompt to a few tight sentences — concrete, no storytelling.

### Step 5a: Test hooks and tunables (Prompt 1)

Autonomous verification only works when the game can play itself on a hidden, silent simulator. Prompt 1 MUST add both blocks near the top of `src/app_<game>.h`; `<GAME>` is a short upper-case game prefix (e.g. `TD` for till_dawn), the same in all three names (the orchestrator records them as `test_hooks`; its hidden-simulator tool passes them as `-D` defines, hence the `#ifndef` guards):

```c
//// TEST HOOKS //// release and device builds keep these defaults; agent test builds flip them
#ifndef <GAME>_DEBUG_AUTOPLAY
#define <GAME>_DEBUG_AUTOPLAY 0      // 1 = the game plays itself (scripted inputs, no title tap, restarts rounds)
#endif
#ifndef <GAME>_MUTE
#define <GAME>_MUTE 0                // 1 = no sound at all (agent test builds; see Step 5b for the audio check)
#endif
#ifndef <GAME>_DEBUG_ROOM_PLANE
#define <GAME>_DEBUG_ROOM_PLANE (-1) // 0..5 = playfield pinned to this face (no tilt needed); -1 = normal
#endif

//// TUNABLES //// every pace number from GDD §4 Tunables; balance passes change only this block
static const uint32_t PLAYER_STEP_TICKS = (uint32_t)(OCT_1SEC_TICKS * 12 / 10); // 1.2 s (GDD), expected to move
```

- **Autoplay** feeds the game's own input paths (a scripted tilt direction instead of reading gravity, a tap or twist at fixed ticks), never bypasses game rules, is deterministic (tick-based script, or `OCT_random` inside `on_tick`), starts PLAYING without the title tap and restarts after win/lose. **Every prompt that adds a mechanic extends the script** so the screenshots show that mechanic; a bot that stands still proves nothing.
- **Mute**: every sound goes through one helper (Step 5b) that compiles to nothing under `<GAME>_MUTE`.
- **Room plane**: wire it where the game chooses its playfield face (face-up at start, tilt); games without one define it and leave it unused.
- **Tunables**: named `static const` values in ticks (`OCT_1SEC_TICKS` = 20), one comment per line with the GDD value and whether it is expected to move. Later prompts reference the names; no magic numbers elsewhere.

### Step 5b: Music and sound prompts

- **One helper**: `void playSound(int32_t id, int32_t volume)` — a no-op under `<GAME>_MUTE`, otherwise `SND_play`; a `playSoundAt(id, volume, quad)` twin for placed sounds. Ids resolved once in `on_init` with `SND_getAssetId("<name>.mp3")` (checked `> 0`).
- **Mixer**: `SND_play` ADDS a voice; each module mixes up to **6 voices**, shared with system chimes; a full mixer refuses the new sound (returns 0, nothing is cut). Plan music (1-2 voices) + up to ~4 effects; keep source peaks moderate (the mix saturates). Return values differ per module: never branch game logic on them.
- **Music bed**: no loop or stop API — keep a `MUSIC_LOOP_TICKS` counter and re-issue `playSound(musicId, MUSIC_VOLUME)` from `on_tick` whenever it runs out, in the states that have music (deterministic on all 8 modules). The period is the loop's measured length: `music_loop_ticks` from the orchestrator's context (printed by `sound_kit.py loop` at Stage 3), else `(duration_ms * OCT_1SEC_TICKS + 999) / 1000` with the `music` sound's `duration_ms` read from the manifest **at implementation time** (Stage 3 replaces the planned value). Music around 40-50 under effects at 100. A sound that is playing cannot be stopped: "stop the music" = stop retriggering; `SND_set_mixer(false)` only for "new sound cuts the old" designs.
- **Where it plays**: a plain `SND_play` in game logic plays on all 8 modules (music, win/lose). A sound that belongs to a place uses `SND_play_quad(id, volume, quad)` — only the module currently showing that screen plays it, and it follows the place across twists — e.g. `OCT_TM_quad(&obj->Tm)` of the enemy that growls. The simulator plays placed sounds on the leader regardless (placement only on hardware).
- **One combined sound per moment**: when events coincide (a shot that also kills) play the combined sound from the manifest, not two sounds on the same tick.
- **Verification of audio prompts**: never by listening. The orchestrator checks the simulator's sound-event log (MCP recorder: one `snd`/`sndq` line per start) of a hidden run whose audio output is stubbed, built without `<GAME>_MUTE`; otherwise by code review (each event calls `playSound` once with the right id).

### Step 5c: Saves prompt (only when the GDD has a Saves section)

One prompt, category `secondary`, after the states it saves exist. The prompt spells out the whole record contract of API.md "Saves" (the same shape `new_app -WithSave` scaffolds):
- `src/app_save.h` (create it, or fill the scaffolded one):

  ```c
  #define SAVE_MAGIC   0x54445331u   // four bytes of this game, never 0
  #define SAVE_VERSION 1
  typedef struct { uint32_t magic; uint16_t version; uint16_t size; } saveHeader_t;
  typedef struct { saveHeader_t header; uint32_t best; /* GDD §9 fields, fixed-width */ } saveRecord_t;
  static_assert(sizeof(saveHeader_t) == 8,  "the record header is eight bytes on the wire");
  static_assert(sizeof(saveRecord_t) == 12, "update this when the record changes");
  #define APP_SAVE_SIZE sizeof(saveRecord_t)
  ```

  The header's `size` field holds `sizeof(saveRecord_t)`; the `static_assert` of the record's wire size (a literal byte count) is mandatory: the fallback `.oct` builder reads `APP_SAVE_SIZE` through it. ≤ 512 KB. In `src/app_metadata.h` switch on `#include "app_save.h"` and `#define APP_HAS_ON_SAVE` (+ `APP_HAS_ON_SAVE_SYNCED` when syncing).
- `on_init`: `OCT_save_read(&rec, 0, sizeof(rec))`; trust the record only when it returned `sizeof(rec)` bytes and `magic`, `version` and `size` all match; anything else (0 = a fresh or unreadable area, an older version) → defaults. Never overwrite a good save with a record that was never loaded.
- Write small records at safe moments (end of a round) with `OCT_save_write` (it blocks for the card: never every tick) and in `on_save()` — called on every exit, docking and sleep: write and return, no sound or animation.
- Modules keep separate cards: when saved data drives game logic, call `OCT_save_sync(0, sizeof(rec))` in `on_init` (that is where API.md puts it; a level boundary is fine too, never every tick: it holds the game up to 10 s) and read the record back in `on_save_synced(result)`. On a failed verdict, or when the sync cannot start, every module starts from the same defaults and writes nothing until a later sync succeeds.
- `APP_GUID1` keys the save area (unique per game, scaffolder-owned). Never define `SIM_SINGLE_THREAD` in a game with saves (the save callbacks then run on modules that never initialised).
- Verification: after a round the record holds the new value; a relaunch shows it (the simulator keeps its card files between runs).

### Platform Reminders catalogue

Pick the ones relevant to each prompt (all of them are facts from `templates/app_ai_template/API.md`):
- Every mutable global uses the `TL` macro (8 modules run as 8 threads in the simulator); immutable `static const` tables and the tunables need none
- `OCT_add` returns 0 when the pool is full — check `> 0` before indexing; slot 0 is never a sprite; a freed index is reused at once (check `gObjects[i].Idx == i`)
- `SPRITES_CAP` is the app's own pool, linked into the module's 256 KB together with the code: practical maximum ~1500 objects; up to 512 sprites are drawn per screen (extras silently not drawn)
- Text: 64 label text slots (62 usable) for `OCT_label_set`; use `OCT_label_static` for captions that rarely change; ≤ 128 chars; glyphs need the packed fonts. Fonts draw x2: on screen FONT_1 capitals ~53 px wide, FONT_2 ~31, FONT_3 ~22 (a screen is 240 px); one label per line, lines 2x the line height apart (FONT_1 120, FONT_2 70, FONT_3 50 px); size every text in the prompts from these numbers
- `OCT_add` / `OCT_add_label` with plane 0..5 add the inner border themselves (pass ±120 for screen centres); `OCT_TM_set`, `OCT_TM_move`, `OCT_TM_walk`, tweens and direct `Tm` writes use raw scene coordinates (screen centres ±(120+GAP), plane edge ±276). Screen-filling art (backgrounds, panorama pieces, edge-to-edge tiles) goes at ±`QUAD_FILL` (119.5; raw ±(119.5+GAP)): at ±120 a 2-px background line shows on the inner screen edges
- `OCT_TM_move` and `OCT_TM_walk(..., wrap=true)` cross plane edges; `OCT_TM_change_plane` to the OPPOSITE plane terminates the app — route through an adjacent plane
- Bitmap sprite angles: multiples of 90 only; positive = CCW, 0 = right (+X); tweens never animate `A`
- XSIGN/YSIGN are declared in oct_shared.h — do not redeclare
- `OCT_background` and `OCT_viewports_layout` persist across apps — set both in `on_init` after `OCT_restart`
- `OCT_dev_mode` overwrites the whole mask: `OCT_dev_mode(OCT_dev_mode(-1) | OCT_DEV_TEXT)`
- `OCT_random(lo, hi)`: `hi` exclusive, needs `hi > lo`; only in `on_init`, `on_tick` and input callbacks; draws after `OCT_restart` in `on_init` repeat every launch (make random content in the first `on_tick`); cosmetic per-screen randomness = `OCT_random_local`
- Frame time = `framelen + 1` ticks with our packer (framelen 0 = 20 fps, 1 = 10 fps); `OCT_sequence(..., -1, ...)` keeps the rate
- Transparency `Transp`: 0 = opaque … 31 (`OCT_TRANSP_MAX`) = invisible; ignored by full-colour (RAW565) sprites
- Fullsize sprites always draw above all half-size content; keep `Layer` ≤ ~120
- `Data0` is every sprite's tint (born `0xFFFF`) — never store game data there; hit flashes via `OCT_tint_mode`
- Firmware `OCT_snprintf` knows only `%d %u %ld %lu %zu %Nd %0Nd %s %c %%` (no floats); no `strlen`/`strcmp`; no `double` (-Werror)
- Twists: `on_pretwisted(side)` gets the turning PLANE and may never be followed by `on_twisted` — commit nothing there; `on_twisted(twid, …)`: 0..11 full, 12..23 half (moved nothing), a 180° turn arrives as two calls; the second argument is a timestamp, not a duration
- Taps: `on_tap(tapid = face, count = position in a series, max 7)`, delivered per tap. Per-screen taps (only when the GDD uses them): call the template's `appTapQuad(tapid)` — the scene quad 0..23, or -1 on firmware without the tap source → run the GDD's per-face fallback (`OCT_tap_source` is on octavios `dev`)
- Shake never reaches the game (it always exits to the launcher): `on_shake` stays a stub
- Never define `SIM_SINGLE_THREAD`

**ALWAYS include these four reminders in every prompt:**
- Use explicit type casts — never rely on implicit conversions
- Use only fixed-width types (int32_t, uint8_t, etc.) — never plain int/short/long
- The six always-exported handlers exist: `on_init`, `on_tick`, `on_pretwisted(int32_t side)`, `on_twisted(int32_t twid, uint32_t disconnected_ms)`, `on_tap(int32_t tapid, int32_t count)`, `on_shake` (stub); `on_proc_draw`, `on_save`, `on_save_synced` only together with their `APP_HAS_*` switch; unused parameters referenced as `(void)x;`
- The TEST HOOKS stay at their defaults (0 / 0 / -1) in the source you hand back; test builds set them (compiler define, or a temporary edit that is reverted)

### Step 6: Validate the Prompts

Before finalizing, verify:

1. **Complete coverage** — every GDD section is covered by at least one prompt (incl. Composition, Music & Sound, Saves, Testing & Delivery)
2. **Asset coverage** — every sprite and sound from the GDD asset list appears in at least one prompt (except `launcher_icon`, which only the launcher shows)
3. **Dependency order** — no prompt references code/objects that weren't created in a previous prompt
   - and nothing a later prompt still uses is removed earlier: Prompt 1 replaces the skeleton, so check that every skeleton symbol it deletes (e.g. `MUSIC_LOOP_TICKS` used by `updateMusic()`) is either kept or replaced in the same prompt (the build must compile after every prompt)
4. **Dependencies are explicit** — every prompt lists its dependencies; no hidden assumptions
5. **Categories are correct** — each prompt has the right category from the table above
6. **Self-contained context** — each prompt's "Current State" accurately summarizes prior work
7. **Testable verification** — every prompt says what the 24-screen screenshots of an autoplay test build show (audio: the sound-event log)
8. **No gaps** — executing all prompts in order produces the complete game described in the GDD
9. **Smallest slices** — no prompt could be reasonably split into two smaller testable prompts
10. **Correct API usage** — all referenced functions match `templates/app_ai_template/API.md` / `app_ai_template.h`
11. **Manifest ↔ prompts cross-check**:
    - Every `BMP_<name>` referenced in any prompt exists in `<game>_assets.json`.
    - Animation aliases: `BMP_<base>` requires a `<base>_00` (or `_01`) entry; `BMP_<base>_end` implies a contiguous sequence exists.
    - Every `"<name>.mp3"` referenced in any prompt exists in `<game>_assets.json` sounds.
12. **Manifest validity** (Step 4 rules): `python <skills>/scripts/build_pipeline.py validate --manifest plans/<game>_assets.json` exits 0 (read its warnings too), and by eye:
    - Names `[a-z][a-z0-9_]*`, ≤ 23 characters, unique, not reserved, not a glyph or alias name; every entry has a `description`.
    - Animation frames zero-padded (2 or 3 digits, consistent width) and contiguous, starting at `_00`/`_000` or `_01`/`_001`.
    - No non-fullsize sprite larger than 120×120 (authored sizes); no size that looks like on-screen pixels; every side > 120 has `flags.fullsize`.
    - Every `color: "full"` sprite has `"flags": {"alpha": false}`; `dither` only on full colour; opaque full-screen backgrounds are full colour.
    - Every sprite has `background` `"key"` or `"opaque"`; every `"full"` or `flags.bg` sprite is `"opaque"`.
    - Sounds: an allowed `event_type`; a music bed (`"music"`) unless the GDD explicitly says "no music"; one combined sound per coinciding moment.
    - `_style` exists (60-120 words); a `launcher_icon` sprite exists (160×160 palette fullsize, `background: "key"`); the `icon` object says palette 120/240 when the GDD wants transparent corners on the launcher; every panorama piece is listed under `_panoramas`.
13. **Generation-prompt rules** (Step 4a):
    - Every sprite has a non-empty `gen_prompt` naming subject, orientation and framing; frames name their phase and what stays identical; effects say "no characters".
    - No `gen_prompt` says "transparent background", a pixel size, or repeats the `_style` paragraph.
14. **Test hooks** — Prompt 1 adds the TEST HOOKS and TUNABLES blocks; every mechanic prompt extends the autoplay script; every sound goes through the mute-gated helper.
15. **Sound** — the music bed is retriggered from `on_tick` with the manifest duration; sounds that belong to a place use `SND_play_quad`; no game logic depends on `SND_play` return values.
16. **Saves** — present exactly when the GDD has a Saves section, with the whole record contract of Step 5c (magic, version, size field, size check on load, the `static_assert` of the wire size, `APP_SAVE_SIZE sizeof(saveRecord_t)`, the sync in `on_init` and its failure path).
17. **Animation placement** — every full-colour fullsize animation was explicitly requested; two animated full-screen (fullsize) pictures on screens sharing a physical module are noted (owner's guideline, informational until confirmed), never a reason to rework the prompts.
18. **Prompts vs the GDD's screens** — read each prompt's placements against the GDD screen map and flow states: which font each text uses, what shows in each state (title, round, result), what is hidden when. A swapped font or an object hidden that the GDD shows passes every compile check and costs a review round later.
19. **Prompt 1 compiles** — whatever Prompt 1 removes from the skeleton is no longer used by the code it keeps (a removed constant still read by a kept helper is a compile error on the first coder run).
20. **Text fits** — every text's on-screen width from the font numbers in the catalogue (fonts draw x2) is under 240 px per screen, or the prompt splits it into one label per line.

## Prompt Writing Rules

1. **Be explicit** — specify exact API calls, parameter values, coordinates, colors. No ambiguity.
2. **Include coordinates** — when placing sprites, provide exact plane, x, y using XSIGN/YSIGN, and say which coordinate system (`OCT_add` with the border added, or raw scene coordinates for `OCT_TM_set`/`Tm`).
3. **One behavior per prompt** — each prompt has a single clear goal.
4. **Current State is for humans** — the orchestrator maintains its own JSON context. The "Current State" section is a convenience summary so a human reader can understand the progression.
5. **Reference the API** — every prompt must include: "See `<skills>/templates/app_ai_template/API.md` and `src/app_ai_template.h` for API details and engine patterns. Do NOT copy demo code."
6. **Remind constraints** — include only the platform constraints relevant to the current prompt (from the catalogue), plus the four mandatory reminders.
7. **Verification is mandatory** — every prompt ends with what the screenshots (or the sound log) show and at which moment of the autoplay run.
8. **Category is mandatory** — every prompt must have a category from the table above.
9. **Dependencies are mandatory** — every prompt must list its dependencies explicitly.
10. **Explicit type casts** — all prompts must instruct agents to use explicit casts for every narrowing, widening, or cross-type assignment.
11. **Fixed-width types only** — `int8_t`, `int16_t`, `int32_t`, `uint8_t`, `uint16_t`, `uint32_t`, `size_t` — never plain `int`, `short`, `long`.
12. **Handlers** — the six always-exported handlers exist in every prompt's code; `on_proc_draw`, `on_save`, `on_save_synced` only with their `APP_HAS_*` switch in `src/app_metadata.h`. Never build gameplay on shake (the engine always exits to the launcher). Unused parameters are referenced as `(void)x;`.
13. **Coordinates and the border** — `OCT_add` with plane 0..5 adds the inner border (GAP) itself; raw scene coordinates (`OCT_TM_set`, `Tm`, tweens) do not. Name which one a coordinate is.
14. **Angle convention** — when specifying angles (Tm.A, OCT_add `a` param, OCT_TM_walk direction), note that positive = CCW, 0 = right (+X).
15. **Asset references are manifest-exact** — every `BMP_<name>` or `"<name>.mp3"` in a prompt must literally match an entry in `plans/<game>_assets.json`. Do NOT invent names, do NOT rely on the packer's name normalization.
16. **Numbers come from the tunables block** — prompts name the tunable, never a bare number for pace.
17. **Test hooks grow with the game** — every mechanic prompt says how the autoplay script exercises it.

## Output

The final output is TWO files:
- `plans/<game_name>_prompts.md` — implementation prompts
- `plans/<game_name>_assets.json` — asset manifest (schema_version 1)

After writing, provide a summary:
- Total number of prompts generated
- Manifest totals: N sprites (K animations, P panorama pieces, the launcher icon), M sounds (music yes/no) — confirm every sprite carries a `gen_prompt` and a `background`, and that `_style` exists
- Rough grouping (e.g., "Prompts 1-3: foundation, 4-7: core mechanic, 8-10: UI")
- Dependency graph overview
- Any GDD gaps or ambiguities resolved with assumptions
- Estimated complexity (worst-case objects vs SPRITES_CAP, function count)

Then **return control to `cube_orchestrator`** — do NOT invoke `cube_asset-builder` yourself. The orchestrator runs the Stage 2→3 boundary (checkpoint in stepwise mode; auto-accepted in autonomous mode) and routes to Stage 3.

**Why the manifest quality matters.** Stage 3 refuses to generate unless every sprite carries a non-empty `gen_prompt`. Codex draws from `_style` (through STYLE.md and the style frame the user approves) plus each `gen_prompt`, and a strict reviewer rejects every asset that breaks `cube_art-director/references/QA_RULES.md` until it passes — vague prompts cost regeneration rounds, not quality.
